# 工作台前端审计（以产品规划为标准）

> 状态：基线评估
> 审计日期：2026-08-03
> 标准：`product-vision.md`、`product-modules.md`、`architecture.md`
> 范围：`apps/workbench/src` 当前代码，回答“用户连上本地运行时后，能不能真正走通一条业务闭环”

本审计与 `frontend-audit.md` 的区别：那份以“代码结构是否整洁”为标准（拆分、
复用、Pinia、路由），本审计以**产品规划要求**为标准。核心问题不是“组件拆没拆”，
而是“**每个页面连上运行时后，用户能不能完成一个真实任务，断在哪一步**”。

## 总体结论

工作台**不是空壳宣传页**，也不是纯静态演示。`applyProjectView`
（`WorkbenchApp.vue:1162`）确实把运行时的活动、内容、任务、产物、回执、报告
映射进了页面。多数页面具备真实读写能力。

但“**像宣传页**”的感觉有真实根源，共三类：

1. **演示数据与真实数据混在一起，用户无法区分**（最影响信任）。
2. **多个页面只有“读”，没有“写”闭环**（看得到、动不了）。
3. **产品第一原则“AI 是主要创作者”零入口**（最大的功能缺口，但被后端阻塞）。

判定标准图例：

- ✅ 连上运行时后能走通产品规划要求的闭环
- 🟡 部分闭环：能读/能部分写，但有断点
- ❌ 产品规划要求的能力缺失或无法闭环

## 逐页闭环评估

### 1. 发布活动 — ActivityListPage.vue + ActivityDetailPage.vue

**产品规划要求**（product-modules “发布活动”模块树）：先主题→选渠道→规划内容→
生成素材→组装成品→发布安排→回执→监测。活动详情要展示内容组、渠道内容、活动
产物、发布安排、人工介入、发布记录、数据表现、活动报告、活动时间线。

| 闭环步骤                       | 状态 | 证据                                                                                                    |
| ------------------------------ | ---- | ------------------------------------------------------------------------------------------------------- |
| 创建活动（主题+渠道+视频计划） | ✅   | `ActivityListPage.vue:100-149` 真实表单，`emit('save-activity')` 调 runtime                             |
| 选择目标渠道（仅项目已启用）   | ✅   | `:112-117` 从 `enabledChannels` 渲染，符合“活动只选项目已启用渠道”                                      |
| 保存渠道内容                   | 🟡   | `:151-189` 表单存在，但**需手动填写正文**，无 AI 生成入口                                               |
| 确认拍摄大纲                   | ✅   | `:293-302` `confirm-video-plan`，runtime 活动可操作                                                     |
| 调整录制 viewport              | ✅   | `:251-275` 仅 runtime 活动可改，生成新版本                                                              |
| 建立发布安排                   | ✅   | `:339-346` `create-publication-plan`，真实写操作                                                        |
| 活动详情完整业务对象           | 🟡   | `ActivityDetailPage.vue` 有主题/渠道/任务/内容组/产物，但**缺审核与修改、发布记录详情、数据表现时间线** |

**断点**：内容生成依赖手动输入（AI 入口缺失，见“产品第一原则缺口”）。
**符合边界**：演示活动明确标注“演示活动只读”（`:289`），不伪装 runtime 数据。

业务栏目；任务详情要显示所属项目/活动/内容/渠道/当前步骤/尝试历史/日志/预览。

| 要求                              | 状态 | 证据                                                                                                                |
| --------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------- |
| 全局/项目共用同一数据源           | ✅   | 同一组件，`activeTaskScope` 切换范围（`:44-47`）                                                                    |
| 任务三分类                        | ✅   | `taskCounts` 制作/发布/监测（`:48-52`）                                                                             |
| 开始/取消/重试/录制               | ✅   | `:111-131` 四个操作都 emit 到 runtime，带 pending/error 状态                                                        |

| 尝试历史/运行事件                 | ✅   | `:89-106` 从 `task.attempts`/`task.events` 渲染                                                                     |

**符合规划**：这是全工作台**最贴近产品模型**的页面 —— 任务边界、范围投影、
执行操作三者都对。主要缺陷是步骤展示仍部分静态。

## 跨页面的结构性问题（按对用户的影响排序）

### 问题 1：演示数据与真实数据混合（最影响信任）

**现象**：`applyProjectView:1219-1226` 用 `[...runtimeCampaigns, ...静态种子]`
合并。连上 runtime 后，真实活动和种子里的假活动**同时显示**，仅靠右上角
“运行时已连接”药丸区分。

**违反规划**：product-vision 成功标准要求“不能把演示数据伪装成真实状态”。当前
虽然每个活动有 `selectedCampaignIsRuntime` 标记（`ActivityListPage:251` 据此
禁用编辑），但**列表层不区分**，用户看到一堆活动不知道哪些是真的。

**建议**：runtime 连接后，静态种子活动要么隐藏、要么明确打“演示”水印，不能
与真实活动平铺。

### 问题 2：产品第一原则“AI 是主要创作者”零入口

**现象**：全工作台无任何 AI 创作入口。`ActivityListPage:154` 注释“手动测试入口 ·
AI/MCP 接入后复用同一接口”，`AssetLibraryPage:82` “编辑素材（等待应用服务）”disabled。

**违反规划**：product-vision 原则 1“AI 是主要创作者”是**产品第一原则**，不是普通
未闭环项。当前工作台实质是“内容审核/管理后台”，未达到“控制台”定位。

**边界约束**：这不是前端能独立解决的 —— 前端调不到 AI（架构原则：交互式 AI
来自 MCP 主机）。**被 V0.3.3 MCP AI 闭环阻塞**。

**建议**：前端先留明确占位（“需经 AI 对话生成”提示），不硬做按钮。真正的入口
等 V0.3.3。

### 问题 3：任务步骤仍是硬编码两步

**现象**：`WorkbenchApp.vue` 的 `taskToProjection`（约 :637-648）返回固定两步
“准备活动内容 / 执行制作阶段”，**不是从任务事件驱动**。TaskBoardPage 同时渲染
了这个 steps 和 StatusRail。

**违反规划**：product-modules “任务内部步骤”要求任务详情显示“当前步骤、步骤进度”，
且视频制作任务应有生成脚本→分镜→录制→预览帧→合成→字幕→变体等多步。当前两步
无法表达真实任务生命周期（queued→generating→...→monitoring）。

**注意**：`StatusRail.vue` 和 `taskLifecycleProjection`（model.ts）已存在，可能是
intended 的真实步骤源，但 TaskBoardPage 同时渲染了两套，造成混乱。

**建议**：统一用 `taskLifecycleProjection`，删除硬编码两步。

### 问题 4：多个“读”页面缺“写”闭环

**现象**：OwnerInboxPage（按钮永久 disabled）、ProjectReportsPage（纯展示）、
AssetLibraryPage 的“编辑素材”按钮 disabled。

**违反规划**：product-modules 要求人工接管后“继续执行的主要位置是活动详情”，
报告要能下钻。当前多个页面是单向展示。

**建议**：为 OwnerInbox 加“跳转对应任务”入口；报告加时间线下钻；这些是纯前端
可做的闭环补齐。

## 收口建议（按产品价值排序，非代码结构）

1. **演示/真实数据分离**（问题 1）—— 纯前端，收益最大，直接影响“是不是宣传页”
   的观感。
2. **OwnerInbox 操作闭环**（问题 4）—— 加跳转任务、接完成/取消，让最像空壳的
   页面活起来。
3. **任务步骤统一用事件驱动**（问题 3）—— 删硬编码，用 taskLifecycleProjection。
4. **AssetPreview 补元信息**（图片尺寸、视频时长/画幅、音频时长）—— product-modules
   明确要求。
5. **AI 创作占位**（问题 2）—— 留明确提示，等 V0.3.3。不要在结构未定时做视觉统一。

**明确不做**：视觉门禁（按钮/箭头/焦点统一）应放在结构稳定后，否则是返工。
