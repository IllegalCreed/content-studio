# 工作台前端审计

> 状态：V0.2 前端结构收口清单
> 审计日期：2026-08-03
> 范围：`apps/workbench/src` 当前代码，不把静态演示数据误认为运行时能力

这份审计解决一个实际问题：工作台必须让用户看清“总览 → 项目 → 发布活动 →
执行任务/活动产物”的关系，同时保持 Vue 只是控制面，不能在前端复制一套生产、
录制或发布引擎。

不可用时，页面必须明确显示“演示数据/只读”，不能把演示数据伪装成真实状态。

## 产品闭环复核（参考 `frontend-audit-product.md`）

这份产品审计补充了代码结构审计容易忽略的判断：页面是否能把一次真实工作做完。
核对当前代码后，结论如下：

- **演示/真实数据混合**：问题成立，已在本轮修正。运行时健康后，活动和任务只使用
  运行时返回的数据；只有运行时不可用时才保留静态只读演示。运行时返回空列表也会显示
  空状态，不会偷偷补入演示活动。
- **AI 是主要创作者**：缺口成立。当前“保存渠道内容”仍是人工测试入口，AI 生成文章、
  图片、脚本和视频大纲的正式入口要等 MCP AI 闭环，前端不能自行复制生成引擎。
- **任务步骤**：需要区分数据来源。运行时任务通过 `taskLifecycleProjection()` 按任务状态和
  事件计算阶段；`model.ts` 中固定的多步内容只属于静态演示任务，不代表运行时任务的真实
  步骤。后续要让演示数据也复用同一套阶段投影，避免用户看到两种表现。
- **待人工处理**：待人工页现在会逐条展示所有 handoff，并为已建立任务提供“查看对应任务”，
  可以回到项目任务面板继续查看上下文；完成/取消 handoff 的真实写操作和活动详情中的回执
  回写仍待 runtime 接口接通。
- **活动详情业务中枢**：本轮已补“活动业务进度”和“渠道结果”区，静态演示活动也会显示
  内容组；运行时页面展示发布安排、成功/失败回执、公开地址和最新监测指标来源。按渠道
  多时间点的完整报告时间线仍待后续实现。
- **全局渠道字段语义**：已将容易误解的“项目策略 / 可监测指标 / 下一步”改成“当前项目状态 /
  平台支持的指标 / 账号或适配器状态”。项目绑定仍只在项目概览修改；指标明确是平台能力说明，
  不冒充实时监测数据。渠道详情中的项目区已收缩为“当前项目引用”摘要，并补充项目账号、
  交付方式和平台格式限制，避免用大段边界说明占据面板却不给用户决策信息。
- **素材和报告**：素材预览已经能显示文字/图片/视频/音频，但尺寸、时长、画幅、校验和、
  真实保留策略仍未完整展示；报告目前展示指标摘要和活动跳转，按渠道时间线及指标来源
  仍是后续工作。
- **多项目总览**：当前示例仍是单项目，跨项目注册表尚未接入，不能把当前项目数字说成
  已完成跨项目聚合。

## 逐项审计结果

### 1. 信息架构与语义

- **符合规划**：左侧已经按“全局控制台 / 当前项目”分组；项目渠道账号在项目概览
  配置，活动只选择项目已启用渠道。
- **已修正第一步**：活动列表已经拆成 `ActivityListPage.vue`，活动详情使用独立路由；
  列表负责筛选、创建和进入详情，详情负责活动业务对象本身。
- **已完成第二轮**：活动、任务和报告的原始数据转展示数据逻辑已集中到 `projections.ts` 的
  `activityToCampaign()`、`taskToProjection()`、`runtimeReports()`；工作台只负责提供
  运行时数据和项目账号别名，页面组件不再自己理解 core 类型。

### 2. 活动、任务、任务阶段

- 活动是业务对象，状态来自 `PublishingActivity.status`：`draft`、`planned`、
  `active`、`completed`、`archived`。
- 任务是执行记录，类型为制作、发布、监测，状态来自任务生命周期：
  `queued → generating → recording → composing → awaiting-owner → published → monitoring`，
  另有 `failed`、`cancelled` 终态/分支。
- `taskLifecycleProjection()` 已经根据任务和事件生成任务阶段；静态演示任务也通过
  `demoTaskProjection()` 使用同一套生命周期计算，因此演示和运行时不会再出现两套阶段名。
- **UI 规则**：活动详情显示“活动状态”；任务面板显示“任务状态”和“任务阶段”。两者
  不再使用“活动步骤”这个叫法。

### 3. 状态与路由

- Pinia `workbench` store 已承接活动详情页的运行时刷新和视频计划操作。
- **已完成第一轮**：Pinia `workbench-ui` 已集中保存当前模块、任务范围、活动/任务/素材/
  渠道账号选择和素材筛选；活动、任务、素材、渠道页面会把当前选择写入 URL query，
  刷新或复制链接后可以恢复对应上下文。运行时连接、加载和连接错误也已由 Pinia
  `workbench` store 统一管理；运行时业务快照也已改为由同一个 store 持有，活动/任务等
  投影计算仍留在工作台编排层。当前仍有弹窗和动作错误留在编排层，后续再继续迁移，
  避免一次改动过大。

### 4. 功能闭环

- 已闭环：项目渠道绑定 → 活动创建 → 视频计划版本/视口修订 → 活动详情确认 → 任务
  面板查看 → 本地任务取消/开始/录制/重试。
- 已闭环：活动产物预览 → 用户明确晋升为项目素材 → 清理预览。
- **未闭环**：AI 生成文章、图片、脚本的实际入口还未接入；发布计划目前只在内容卡片
  上有入口，发布/监测任务在所有活动场景下的自动创建还需要服务层补齐；活动报告仍
  缺少按渠道的时间线和指标详情。
- **明确边界**：任何“发布”按钮都只能进入本地发布准备或 owner handoff，不能直接写入
  真实渠道。

### 5. 组件与样式

- 已拆分：`AssetPreview`、`VideoJobPanel`、`StatusRail`、`SelectMenu`、活动详情页和
  Pinia store。
- **已完成第一轮拆分**：`OverviewPage`、`ProjectOverviewPage`、`ActivityListPage`、
  `TaskBoardPage`、`ChannelManagementPage`、`AssetLibraryPage`、`OwnerInboxPage` 和
  `ProjectReportsPage` 已成为独立组件；`WorkbenchApp.vue` 只保留工作台壳、页面状态和
  事件编排。
- **已修正**：主工作台和详情页现在共用 `WorkbenchShell.vue`；`WorkbenchApp.vue` 只保留
  运行时刷新、异步动作和页面编排逻辑，活动/任务展示投影已移到独立模块。
- 共享按钮、表单控件、下拉弹层和焦点样式应集中在基础样式/组件中；禁止页面各自复制
  字号、内阴影、箭头定位和禁用态。

### 6. 可访问性与交互基线

- 活动详情的运行时错误、加载和操作结果已经使用 `aria-live`。
- 已补：全局跳过链接、明确的主内容 landmark、活动表单控件 `name`、素材图片懒加载和
  `aria-live` 错误播报；详情页和新页面导航使用链接语义。
- 待补：表单 autocomplete、长标题/长路径和错误消息的稳定换行。
- 所有图标按钮必须有可读标签；导航是链接，改变状态才使用按钮。

## 收口顺序

1. **路由和详情（已完成）**：保留 `/project/activities` 列表，所有活动卡片进入
   `/project/activities/:activityId`；补路由测试。
2. **状态集中化（第二轮完成）**：选择状态、页面筛选、运行时连接状态和共享业务快照已
   迁移到 Pinia，并与 URL query 同步；投影计算、弹窗和具体动作错误仍待下一轮迁移，
   页面继续只负责展示和事件派发。
3. **投影模块化（已完成）**：活动、任务和报告的展示投影已从工作台编排层或通用模型
   拆到 `projections.ts`，并有单元测试；渠道和素材投影仍按同样方式逐步收拢。
4. **页面组件化（第一轮已完成）**：活动列表、任务面板、渠道管理、素材库、项目概览、
   总览、人工处理和报告均已拆分，共享壳已经统一。
5. **闭环补齐**：补 AI 内容生成入口、发布安排/监测任务创建状态、按渠道报告详情；
   每个动作必须有成功、失败、只读演示和权限边界提示。
6. **视觉和交互门禁**：统一按钮、select popup、箭头、焦点、空状态、加载态和移动端
   响应式布局，再跑全量测试和生产构建。
