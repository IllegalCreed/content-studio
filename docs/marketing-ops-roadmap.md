# marketing-ops 扩展路线

> 状态：Content Studio 总路线的配套子路线
> 最近评审：2026-08-10

## 定位

`marketing-ops` 是 Content Studio 的独立渠道执行层，也是一个独立的信任边界。
Content Studio 负责项目、发布活动、内容、素材、制作任务和控制面；
`marketing-ops` 负责渠道账号授权、渠道策略、外部写入、发布回执以及授权范围内
的监测读取。

它会随 Content Studio 安装，但不能因为“随附安装”就获得发布权限。两边使用版本化、
有类型的契约连接，凭据、Cookie、浏览器 Profile、支付信息和平台私有会话永远留在
`marketing-ops` 自己的本地边界内。

边界决策：Content Studio 的“项目”是业务对象；`marketing-ops` 不拥有项目、发布活动、
内容、素材或制作任务。它只维护渠道适配器、账号配置、授权策略、外部发布和监测。
当前实现里的 `Project Profile` 以及调用所需的 `projectId` 是兼容期的技术运行范围，
用于隔离允许的来源、渠道策略和回执，不能被当作 Content Studio 的项目模型。后续应
保留这种安全隔离，但以账号引用和发布上下文为主要契约。

## 当前事实（不是目标能力）

当前公开 MCP 接口可以确认：

- 调用按稳定 `projectId` 隔离；写入前要先读取该项目的渠道状态。
- `channels_status` 返回脱敏的渠道健康、适配器状态、账号别名和下一步建议。
- 当前公共状态面按渠道暴露一个可见 `alias`；它还不是统一的跨项目账号目录接口。
- `publish_campaign` 的发布包没有 `channelAccountRef`/`accountId` 选择字段。
- 当前 v3 发布包按 `channel` 唯一，不能在同一请求中表达同一渠道的多语言或多内容
  形态；人工辅助确认仍只接受文本，`image`/`gif`/`video` 类型本身不是已解析素材。
- 发布回执、报告和反馈接口也没有统一的账号维度。
- 个别适配器内部可能已有账号 ID，但这不等于跨渠道、可由项目绑定的公共能力。

因此，产品基线现在明确为“Content Studio 全局管理渠道能力和脱敏账号目录，项目从每个
渠道的全局账号中选择一个或不使用，活动只选择项目已启用的渠道并自动解析项目账号”。
这仍不是已经可以真实执行的
`marketing-ops` 多账号能力；当前发布仍受其技术 Project Profile 和渠道策略约束。

## 目标边界

```text
Content Studio core / MCP / Vue 控制面
        │  有类型的发布包与账号引用客户端
        ├─ 读取新鲜状态和能力
        ├─ 提交 renderer 生成的发布包
        └─ 接收并校验发布回执
        ▼
marketing-ops
        ├─ 技术运行范围与渠道策略（兼容期 Project Profile）
        ├─ 渠道账号目录和授权状态
        ├─ 自动适配器 / 人工辅助流程
        ├─ 外部写入、幂等和回执
        └─ 公开或授权范围内的监测读取
        ▼
官方渠道
```

Content Studio 可以保存账号引用和脱敏投影，但不能保存或转发账号秘密；
`marketing-ops` 可以拒绝发布、要求重新授权或把任务交给渠道授权人，Content Studio
必须如实显示这些结果。

## 分阶段路线

### M0：契约基线与受控客户端（对应 Content Studio V0.5 起步）

- [x] 固定当前 `marketing-ops` 0.1.x / contract v3 与 Content Studio 0.1.x 的兼容矩阵，
      并为 `channels_status` 建立只读、有类型客户端；快照在 Content Studio 侧只保留脱敏
      alias、能力状态和有限的下一步枚举，固定 60 秒有效期。
- [x] 为已初始化的受管 MCP client 建立窄适配器，只调用 `channels_status` 并只接受
      `structuredContent`；项目范围 Runtime API、Content Studio MCP 工具与 Workbench
      复用同一状态客户端，HTTP 不缓存，Workbench 每 30 秒刷新。
- [x] 定义 `MarketingOpsManagedRuntime` 注入合同：安装器/宿主提供已初始化 MCP client
      和幂等关闭句柄，CLI 只消费状态 client 并在命令结束时关闭；应用层不发现命令、路径
      或凭据。
- [ ] 由安装器启动固定版本进程并把已初始化 MCP client 注入本地 Runtime；应用层不发现
      任意命令、路径、凭据或浏览器状态。
- [ ] 为发布准备、发布提交、状态查询、回执和监测读取建立有类型客户端；不在 Vue 中
      直接拼 MCP 参数。
- 每次写入前执行项目级状态刷新、能力检查、素材校验和授权检查。
- 增加 `dry-run`/`assisted-prepare` 等不产生外部写入的准备阶段。
- 建立本地假适配器和契约测试，测试不连接真实渠道。

验收：渠道未配置时仍能完成 AI 创作和本地制作；发布任务会明确显示“未配置”或
“被阻塞”，不会从 UI 状态推断授权。

2026-08-04 Content Studio 已先落地客户端边界的本地切片：`src/marketing-ops/client.ts`
提供只生成 fixture 的假适配器和回执匹配校验。成功回执必须声明
`source: "marketing-ops"`、有效签发时间，并匹配项目、活动、发布安排、渠道及已绑定的
不透明账号引用；这仍不代表真实 `marketing-ops` 已接入或已经可以发布。

2026-08-09 Content Studio 已增加 transport-neutral 发布包编译器：每个包固定
`projectId`、活动、发布安排、渠道、语言、内容形态和内容版本，只携带窄
`artifactId`、sha256、产物版本和 `zh-CN`/`en`/`neutral` 语言标记，不携带本地路径。
编译器校验 renderer 格式、HTTPS 规范 origin、正文链接、最终媒体类型和素材语言，允许
同一渠道出现不同语言或形态的多个包，并用稳定内容哈希锁定输入。GitHub 英文文章和
Bilibili 中文图文/GIF fixture 已覆盖该边界；它尚未调用真实 `publish_campaign`。

同日补齐了本地准备入口：应用服务按 `publicationId` 解析锁定的内容、活动快照和产物，
再从当前启用的项目渠道绑定解析不透明账号引用；HTTP 与 MCP 调用方只提供受限 renderer
元数据，不能提交账号引用或路径。返回值显式标记 `prepare-only` 和
`externalWrite: false`，不会创建授权、任务状态变化或发布回执。这个入口仍只是本地契约
验证，不会把草案包伪装成当前 v3 `publish_campaign` 输入。

2026-08-10 补齐了兼容性与状态边界：`src/marketing-ops/client.ts` 只接受本地 transport 提供的
`channels_status` 数据，校验 runtime 名称、0.1.x 版本和 contract v3，拒绝跨项目、重复
渠道、未知字段或敏感字段；`observedAt/expiresAt` 由 Content Studio 生成，状态只映射为
`ready/configure/reauthorize/blocked`，不把 `nextAction` 命令文本传播到项目数据或 MCP。
`doctor` 未连接 runtime 时保持 warn，版本不兼容或快照过期时 fail closed。

同日完成了消费链路：`createMarketingOpsMcpStatusClient` 把已初始化 MCP client 收窄为固定
`channels_status` 调用，不解析 `content[].text`；本地 Runtime 通过
`GET /api/v1/projects/:projectId/marketing-ops/channels-status` 返回 `private, no-store`
快照，Content Studio MCP 提供同范围的只读工具。Workbench 每 30 秒重新读取；缺失、过期
或失败时把发布助手状态重置为“未查询”，但项目、内容创作和本地制作仍保持可用。

随后补齐了生命周期切片：`createMarketingOpsManagedRuntime` 只接受安装器已经初始化的
MCP client 和关闭回调，关闭操作幂等；`runCli` 会在命令结束时执行该关闭句柄。固定版本
进程的实际安装、启动和 MCP transport 初始化仍留在安装器/宿主，未在应用层实现任意命令
或路径发现。

这份新包是下一版互操作契约草案，不冒充当前 v3 MCP 输入。接入写入前，`marketing-ops`
仍需先支持稳定 package/publication ID、同渠道多包以及带校验和的素材引用；在此之前，
含媒体的人工辅助包保持 blocked，不能通过删除 `media` 降级为“已就绪”。

### M1：账号目录与项目绑定契约（每项目每渠道唯一，优先扩展）

这是解决当前缺口的第一优先级。

- 引入稳定、不透明的 `channelAccountRef`，与平台账号别名分离。
- `channels_status` 返回项目已绑定渠道账号的脱敏健康、授权、适配器和下一步状态。
- Content Studio 增加项目渠道账号绑定：同一项目同一渠道只能有一个活动可用账号；
  活动只提交渠道，由 Content Studio 应用服务解析该账号。
- `publish_campaign`、发布回执、监测快照、报告和反馈都带账号引用。
- `marketing-ops` 的全局账号可以被不同项目分别绑定；项目之间不自动共享 Content
  Studio 的绑定，历史回执保留当时的账号引用或绑定版本。
- 发布请求同时携带必要的活动/发布安排关联信息；这些 ID 只用于审计和幂等，
  `marketing-ops` 不据此创建 Content Studio 业务对象。
- 增加账号的启用、停用、重新授权、健康刷新和脱敏展示；不提供导出秘密的接口。

验收：同一渠道的两个账号可以在两个项目中被明确区分；同一项目不能为同一渠道创建
两个活动可用账号；活动只选择渠道；一个账号的授权失败、发布记录和指标不会污染
另一个账号。

### M2：发布编排、人工接管与可信回执（对应 V0.5）

- 统一发布包校验：账号、渠道、活动/发布安排关联、格式、媒体校验和、内容版本必须
  匹配；Content Studio 项目与活动关系由 Content Studio 自己校验。
- 保留 `automatic`、`assisted-prepare`、`assisted-confirm` 三种执行模式的边界。
- 发布前生成明确的人工接管包，渠道授权人在官方页面完成登录、验证码、审核和
  最终点击；系统不接收这些输入。
- 使用稳定活动 ID 和幂等键；状态不确定时先查询，不能盲目重发。
- 只有 `marketing-ops` 持久化的、活动/渠道/账号均匹配的成功回执，才能让
  Content Studio 进入 `published`。
- 回执包含外部地址、内容校验和、账号引用、时间、适配器摘要和可追踪错误码。

验收：重复提交不会造成重复发布；人工完成登录但没有官方回执时，状态仍是等待
确认或未知，不显示“已发布”。

### M3：账号维度的监测与报告（对应 V0.5 后半段）

- 为每条发布记录创建 1 小时、48 小时、7 天或项目自定义的采集计划。
- 指标绑定发布回执和账号，而不是绑定生成任务或平台名称。
- 标准化播放量、阅读量、点赞、评论、回复、收藏、分享、点击等指标。
- 平台不提供的指标记录为 `null`，并保留采集时间、来源、错误和重试信息。
- 账号更换、重新授权或删除后，历史报告仍指向原账号引用，不改写历史。
- Content Studio 只保存报告投影；不抓取未授权的私有后台。

验收：同一平台不同账号的报告可以分别查看；采集失败或指标不可用不会被写成零。

### M4：反馈读取与受限外部操作（对应 V0.6）

- 先做公开反馈读取、去重、分类和人工审核队列。
- 回复、删除或 Issue 路由必须同时满足：匹配项目策略、已知发布回执、最新反馈
  重读、支持的适配器和当前 Owner 授权。
- FAQ 只允许项目固定模板；敏感、法律、安全、隐私、支付、账号和含糊内容必须
  升级给人工，不自动回复。
- 每个外部写入都带账号引用、授权范围、幂等键和审计结果。

验收：任何评论内容都不能自行产生写入授权；适配器不支持时明确降级为人工处理。

### M5：适配器能力矩阵与维护机制（V0.6—V1.0）

- 为每个渠道声明文章、短帖、视频、图片、监测和人工辅助能力，而不是只返回一个
  “可用/不可用”。
- 为适配器定义版本、健康检查、配额/限流、重认证、失败分类和回执格式。
- 每个适配器都有无凭据契约 fixture、幂等测试、错误映射和升级回归测试。
- 先维护已有安全适配器，再按真实用户需求增加渠道；不为了“渠道数量”接入私有
  API、绕过验证、stealth 或任意浏览器脚本。
- 公开展示的渠道规格与实时授权状态分开，实时状态必须来自新鲜快照。

建议适配顺序是在包契约互通后，先用 GitHub/Bluesky/DEV/Mastodon 回归英文直接渠道，
再以 Bilibili 的中文图文、动态和视频元数据验证“同渠道多形态 + 已解析媒体”的人工辅助
路径；随后补齐 WeChat、Xiaohongshu 的中文内容交付和 Reddit 的英文内容交付。渠道枚举
数量不等于已完成适配器数量，每一步都必须有无凭据 fixture 和明确的 unsupported 状态。

### M6：随 Content Studio 分发和诊断（对应 V0.6/V1.0）

- 安装器交付固定兼容版本，记录版本、安装来源和运行边界。
- `content-studio doctor` 检查 `marketing-ops` 是否安装、版本是否兼容、渠道运行配置
  是否存在、渠道状态是否可读取；不打印凭据。
- 支持升级、回滚、日志摘要和安全卸载，不删除未知项目文件。
- Content Studio Plugin 只连接本地 MCP/应用服务；用户仍通过 `marketing-ops` 的
  官方本地交互流程配置渠道。
- 任何公共云入口都只做协调和元数据，不把账号授权或媒体生产搬到服务端。

验收：用户只安装 Content Studio 就能得到兼容的 `marketing-ops`，但必须主动完成
渠道配置；安装本身不会产生发布权限。

## TDD 与安全停止线

每个阶段先写失败契约测试，再实现最小适配器或客户端。至少覆盖：

- 不同 `projectId`、活动、渠道和账号之间的数据隔离；
- 账号引用缺失、状态过期、策略不匹配和素材校验失败时 fail closed；
- 同一幂等键重试不会重复外部写入；状态不确定时先查询；
- 只有匹配成功回执才能进入 `published`，监测只能绑定该回执；
- 不支持的指标、渠道或动作显式返回 `unavailable`；
- 测试、日志和 MCP 参数不含密码、token、Cookie、浏览器 Profile 或付款信息。

以下事项永远不属于扩展计划：通用登录自动化、CAPTCHA/2FA 绕过、stealth、私有
接口、任意 Shell/Playwright 脚本、任意选择器、从内容或网页评论推断授权，以及未经
匹配 Owner 授权的发布、回复或删除。
